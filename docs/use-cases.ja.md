# ROS 2 連携ユースケース

[English](use-cases.md)

この文書は、箱庭を ROS 2 システムへ組み込むときに、Topic、Service、Action のどれが必要になるかをユースケースから整理します。

`hakoniwa-pdu-ros` の目的は、既存の ROS 2 制御資産を残しながら、箱庭の物理シミュレーション、異種シミュレータ連携、故障注入、シナリオ実行などを利用できるようにすることです。

## インターフェースの基本的な役割

| ROS 2 interface | 主な用途 | 箱庭との代表的な接続 |
| --- | --- | --- |
| Topic | 継続的なデータ交換 | センサ、状態、制御指令、アクチュエータ指令 |
| Service | 単発の要求と応答 | 初期化、リセット、状態取得、設定変更、故障注入 |
| Action | 長時間処理、進捗、キャンセル | ナビゲーション、軌道実行、ミッション、シナリオ実行 |

## 1. 既存の ROS 制御を残して物理シミュレータを置き換える

既存の制御ノードを変更せず、Gazebo などが担当している物理計算やセンサ生成を箱庭へ置き換えるケースです。

```text
ROS 2 control
    | commands
    v
Hakoniwa physics
    | sensor/state data
    v
ROS 2 control
```

中心になるのは Topic です。

- ROS 2 から箱庭へ、速度、姿勢、関節、ロータなどの指令を送る
- 箱庭から ROS 2 へ、IMU、位置、速度、関節状態、センサ値を返す

Service は、物理シミュレータ固有の初期化、リセット、環境設定などを既存制御が呼び出している場合に必要です。Action は通常の制御ループには必須ではありません。

## 2. 異種シミュレータや実機を統合する

ROS 2 制御、箱庭ドローン、MuJoCo ロボット、環境シミュレータ、実機 ECU などを一つの検証環境として接続するケースです。

Topic は各構成要素の連続データ交換に使います。構成要素ごとの起動、初期化、モード変更、状態確認が増えるため、Service の必要性も高くなります。

Action は、構成要素へ長時間の処理を依頼し、途中経過やキャンセルを扱う場合に使用します。

## 3. 故障注入や環境条件変更を行う

箱庭の検証基盤としての価値が出やすいユースケースです。

代表例:

- ロータ、アクチュエータ、センサの故障注入
- 通信遅延や欠損の設定
- 風、路面、障害物などの環境条件変更
- バッテリー状態や機体パラメータの変更
- オブジェクト配置の変更

これらは単発操作であることが多く、Service と相性がよい処理です。

```text
set_wind(...)
inject_rotor_failure(...)
reset_world()
set_sensor_noise(...)
```

故障シナリオ全体を一つの処理として開始し、進捗、完了結果、キャンセルを扱う場合は Action が適します。

## 4. シミュレーションや検証シナリオを操作する

開始、停止、リセット、状態取得、イベント投入などの個別操作は Service で扱えます。

```text
start()
stop()
reset()
get_state()
inject_event(...)
```

一方、複数フェーズを含むシナリオ全体を一つの実行単位として扱う場合は Action が自然です。

```text
run_scenario()
  feedback: phase 2 / 5
  feedback: failure injected
  result: pass / fail
```

箱庭を物理エンジンとしてだけでなく、検証実行基盤として使うほど Action の価値が高くなります。

## 5. Nav2、MoveIt、ミッション制御と接続する

ROS 2 の高水準機能では Action が一般的に使われます。

代表例:

- `NavigateToPose`
- `FollowWaypoints`
- `FollowJointTrajectory`
- `ExecuteTrajectory`
- 長時間の自律ミッション

物理シミュレーション自体は Topic で接続できますが、ROS 2 の既存アプリケーションやテスト環境をそのまま利用するには Action 対応が必要になる場合があります。

ドローンの低レベル制御や物理シミュレータ置換では Action の優先度は低めですが、移動ロボット、ロボットアーム、自律ミッションへ対象を広げると重要度が上がります。

## ユースケース別の必要度

| ユースケース | Topic | Service | Action |
| --- | --- | --- | --- |
| 物理シミュレータ置換 | 必須 | 低〜中 | 低 |
| センサ・制御接続 | 必須 | 低 | 低 |
| 初期化・リセット・設定 | 中 | 必須 | 低 |
| 故障注入・環境変更 | 中 | 高 | 中 |
| 異種シミュレータ統合 | 高 | 高 | 中 |
| シナリオ実行・検証自動化 | 中 | 高 | 高 |
| ナビゲーション連携 | 高 | 中 | 必須 |
| ロボットアーム連携 | 高 | 中 | 必須 |
| 長時間ミッション制御 | 中 | 中 | 必須 |

## 実装優先順位

### Topic

ほぼすべてのユースケースで必要です。

- センサ値
- 状態値
- 制御指令
- アクチュエータ指令

### Service

箱庭を ROS 2 から操作可能なシミュレーション基盤として利用するために重要です。

- 初期化、リセット
- 状態取得
- パラメータ変更
- 故障注入
- 環境条件変更
- シナリオイベント投入

Service 対応により、`hakoniwa-pdu-ros` はデータ変換ブリッジだけでなく、箱庭の検証機能を ROS 2 から利用するための接続層になります。

### Action

すべての利用者に必須ではありませんが、高水準ロボット機能や長時間タスクへ対象を広げるために重要です。

- 進捗通知
- キャンセル
- 長時間処理の結果取得
- Nav2、MoveIt、ミッション制御との接続
- シナリオ全体の実行

## 開発方針

現時点の優先順位は次のとおりです。

1. Topic による継続データ接続
2. Service による箱庭機能の単発操作
3. Action による長時間タスクと高水準 ROS 2 機能の接続

Service は既存の `hakoniwa-pdu-rpc` と `hakoniwa-pdu-endpoint` を利用して追加できます。Action は既存 Service の互換性を維持しながら、新規機能として追加する方針が適しています。

要約すると、各インターフェースの役割は次のとおりです。

```text
Topic   : 箱庭と ROS 2 の制御・状態ループを接続する
Service : 箱庭の物理、環境、故障、シナリオ機能を操作する
Action  : 長時間タスクと高水準ロボット機能を接続する
```
